## Зміна фільтра ботів у Wikimedia (2025)

- Навесні 2025 Wikimedia помітила незвично багато «людського» трафіку, переважно з Бразилії. Виявилося, що це боти, які обходили фільтр.
- 2025-08-28 запустили новий евристичний фільтр ботів. Дані переглядів **перераховано від 2025-03-20**; раніші дані лишилися за старими правилами.
- Після перерахунку людські перегляди Wikipedia за ті місяці були приблизно на 8 % нижчими, ніж рік тому. Wikimedia пояснює це впливом генеративного AI і соцмереж на те, як люди шукають інформацію, і радить обережно інтерпретувати тренди, бо правила фільтра в різні періоди різні.
- **Що це означає для навички:** порівняння «рік до року» через 2025-03-20 частково міряє зміну правил, а не інтерес. Перегляди «на мільйон» це компенсують, лише якщо відфільтровані боти були рівномірно розподілені по розділу. Тому це стоїть у незмінних застереженнях (`caveat.bot_rules`) у JSON і PDF.
- Джерела:
  - [Wikitech: Data Issues, 2025-06-03 — May 2025 spike in bot traffic](https://wikitech.wikimedia.org/wiki/Data_Platform/Data_Lake/Data_Issues/2025-06-03_May_2025_spike_in_bot_traffic)
  - [Diff (блог Wikimedia), 2025-10-17 — New User Trends on Wikipedia](https://diff.wikimedia.org/2025/10/17/new-user-trends-on-wikipedia/)

## Що показали реальні дані (перевірено 25.09.2026)

- Весь uk-розділ за 2024–2026 упав приблизно з 80 до 50 млн людських переглядів на місяць. Тому ріст рахуємо «на мільйон переглядів розділу», а не лише в абсолютних числах.
- uk «Астрономія»: вересневий пік щороку (шкільна сезонність), тож «рік до року» порівнює вересень із вереснем, а визначення сплеску в T12 не зараховує такий пік (SPEC розд. 4).
- cs «Přerušovaný půst»: з `--period 5y` обсяг раніше рахувався за весь період і маленька зараз стаття отримувала high. Тепер обсяг рахується за 24 місяці, з яких рахується ріст.

## Дозволи в Claude Code (перевірено 25.09.2026, Claude Code 2.1.281)

Для розділу README «Як встановити й запустити». Деталі й журнали — `evals/results/p0-haiku-notes.md`, розд. 0 і 6.

- **Найпростіше — викликати навичку самому:** `/wikipedia-demand-signals Порівняй …`. Тоді діє `allowed-tools` з SKILL.md, і обидві команди скрипта (`uv run …`, запасна `python -m uv run …`) виконуються без жодного питання про дозвіл.
- **Коли навичку обирає сама модель** (звичайне питання без `/`), Claude Code питає дозвіл «Execute skill» (так працює будь-яка навичка з `allowed-tools`), а далі `allowed-tools` не діють: на команди скрипта теж буде питання. Щоб його не було, додайте правила в `.claude/settings.json` папки, де працюєте (діють лише в папці, якій ви довірилися при першому запуску Claude Code):
  ```json
  {"permissions": {"allow": [
    "Skill(wikipedia-demand-signals)", "Skill(wikipedia-demand-signals *)",
    "Bash(uv run \"<шлях до навички>/scripts/wds.py\" *)",
    "Bash(python -m uv run \"<шлях до навички>/scripts/wds.py\" *)"]}}
  ```
  `<шлях до навички>` — з прямими скісними рисками, як його підставляє Claude Code (напр. `C:/Users/<user>/project/.claude/skills/wikipedia-demand-signals`).
- **Автоматичні прогони** (`claude -p`, evals) передають ці самі 4 правила прапорцем `--allowedTools`: у недовіреній папці правила `settings.json` відкидаються, а в `-p` будь-яке питання = відмова (SPEC розд. 5).
- Правила дозволяють лише команди самої навички, а не довільний Python чи uv.

## Робоча папка

- Навичка пише результати в `./wds-output/` поточної папки. У T9 модель, коли навичка не спрацювала, склала «звіт» зі старих `result.json` іншої теми, що лежали в папці. Порада для README: не тримати чужі чи старі `wds-output/` у робочій папці (або видаляти перед новим питанням). У SKILL.md додано: не відповідати з файлів у папці замість запуску.
- Тому evals ідуть кожен у новій чистій папці (SPEC розд. 7).
