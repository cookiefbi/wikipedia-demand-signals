# Spec: wikipedia-demand-signals

Статус: **чернетка на рев'ю** · 2026-09-24 · дедлайн кейсу 2026-09-27 23:59

## 1. Мета

Навичка (Agent Skill) для AI-агента, з якою засновники B2C-продуктів оцінюють інтерес до тем у різних мовних розділах Wikipedia: чи зростає інтерес, де він сильніший, наскільки велика аудиторія і наскільки цьому можна довіряти. Результат: коротка відповідь у чаті, графік і PDF на одну сторінку.

**Головний принцип:** усі обчислення й висновки робить код, а агент лише розуміє запит, викликає команду й переказує готовий результат. Тому навичка має надійно працювати на Claude Haiku 4.5.
**Єдиний виняток — вибір статті за змістом.** Чи підходить кандидат до того, що мав на увазі користувач («Learning English» — радіопрограма VOA, а не вивчення мови), код не визначить. Код дає кандидатів з описами й покриттям мов, а агент обирає за короткою процедурою з SKILL.md (розд. 3).

**Користувацькі сценарії** (приклади з завдання + уточнення):
1. «Порівняй зростання інтересу до інтервального голодування в pl і cs за останні два роки».
2. «Чи зростає інтерес до астрономії в uk-Вікіпедії і наскільки цьому можна довіряти?»
3. «Порівняй інтерес до вивчення англійської в обраних розділах і підготуй звіт: які аудиторії досліджувати далі?»
4. Уточнення після першої відповіді: «додай словацьку», «тепер важливіший розмір аудиторії», «зроби звіт українською».

## 2. Стек

- Python ≥ 3.11. Залежності вказані в заголовку скрипта (PEP 723): `numpy`, `matplotlib`. Більше нічого, HTTP через стандартну бібліотеку.
- Запуск через `uv run` (uv ставить залежності сам, `.venv` у репозиторії не створюється). Без uv: `requirements.txt` із зафіксованими версіями.
- Тести: `pytest`; `scipy` потрібен тільки в тестах, щоб звірити нашу реалізацію Mann-Kendall / Theil-Sen.
- Графіки та PDF: matplotlib (`PdfPages`, шрифт DejaVu Sans, який підтримує кирилицю, `ł`, `ř`, `ě`).

# без uv

# тести, лінт, валідація формату

### Контракт CLI

**`resolve <запит> --langs <коди|назви>`** повертає JSON верхнього рівня: `status` (`"ok"`, як у помилок — `"error"`), `query` (запит без зайвих пробілів), `langs` (канонічні коди розділів, напр. `nb` → `no`), прапорець `ambiguous` і `candidates` — до 5 кандидатів, кожен з полями
`qid`, `label`, `description`, `sitelinks` (назва статті для кожної мови або `null`), `sitelinks_total`, `found_via` (`wikidata` | `fulltext` | `both`).
- **Завжди обидва пошуки:** `wbsearchentities` і `generator=search` по en.wikipedia з `prop=pageprops` (один запит). Потім один `wbgetentities` на всіх кандидатів (sitelinks, опис, P31).
- **Сортування:** (1) точний збіг назви/синоніма із запитом (без урахування регістру), (2) позиція в пошуку, (3) покриття потрібних мов, (4) `sitelinks_total`. Кількість мовних версій стоїть **останньою**, інакше «Fasting» обійде «Intermittent fasting».
  - **Позиція в пошуку = сума місць в обох пошуках** (з нуля; якщо кандидата немає в одному з пошуків, його місце там = 10, тобто після останнього результату). Кожен пошук окремо помиляється: Wikidata ставить першим бренд Ford «Mercury», повнотекстовий пошук — острів для «Java».
- `sitelinks_total` рахує лише статті Wikipedia за **allowlist**: ключ sitelink має бути `dbname` відкритого мовного розділу з `scripts/wds_lib/languages.json` (записано з `sitematrix`). Тому не рахуються Wikiquote, Commons, Abstract Wikipedia (`abstractwiki`) тощо.
- **Сторінки неоднозначності** (P31 = Q4167410) не потрапляють до кандидатів: аналізувати їх не можна.
- **Кандидати з 0 статей Wikipedia** (`sitelinks_total = 0`: наукові статті, клінічні дослідження, пісні, картини) теж відкидаються: їх не можна проаналізувати в жодній мові, а Wikidata ще й міняє їхній порядок між запитами. Кандидати, що мають статті, але не в запитаних мовах, **лишаються**: сортування за покриттям і так опускає їх нижче.
- Мова пошуку: `en` (у SKILL.md: «переклади тему англійською»); `--search-lang` для локальних тем, яких немає в en.

**Неоднозначна vs широка тема.** Рішення, чи перепитувати, ухвалює код, а не модель:
- `ambiguous: true`, коли одночасно виконано три умови (рахується по кандидатах, яких бачить агент, тобто до 5):
  - є ≥ 2 кандидати, чия назва чи синонім точно збігається із запитом;
  - кожен із них має статтю **хоча б в одній** із запитаних мов;
  - у другого за кількістю мовних версій не менше ⅓ від першого.

  Правило перевірене на живому API (відповіді записано 25.09): «Java» (мова програмування 123 проти острова 149 статей Wikipedia) і «Mercury» (планета 250 проти хімічного елемента 176) дають `true`; «astronomy» (наука 252 проти журналу 9 без pl/cs/uk; пісня з 0 статей відкидається ще до правила) — `false`. Числа рахуються так само, як у коді: лише статті Wikipedia (allowlist вище). **Числа — на дату перевірки й можуть змінюватися**; тести спираються на записані фікстури (`tests/fixtures/resolve/`), а не на живе API. (У версії SPEC від 24.09 стояло 124/251/253: ручний підрахунок тоді зараховував sitelink `abstractwiki`.) Тоді агент ставить **одне** уточнювальне питання.
- Сторінка неоднозначності серед результатів пошуку сама по собі **не** є ознакою неоднозначності. Для «learning English» вона стоїть першою в повнотекстовому пошуку, але це широка тема, а не неоднозначна.
- Широка тема («астрономія») не є неоднозначною. Агент бере основну статтю, прямо називає це допущенням і пропонує додати пов'язані статті. Без питання.

**Процедура вибору статті (у SKILL.md):**
1. Відкинути кандидатів, чий опис не відповідає запиту (радіопрограма, альбом, журнал, наукова стаття).
2. Якщо точне поняття не має статей у потрібних мовах (для «English as a second or foreign language» немає pl/cs/uk), повторити `resolve` із ширшим терміном («English language») і назвати його заміною теми в `assumptions`.
3. Питати користувача лише при `ambiguous: true` або коли не підійшов жоден кандидат навіть після розширення.
   **Мовні розділи не названі** (приклад 3 із завдання: «у вибраних нами мовних розділах») — теж одне уточнення, але з готовою пропозицією набору (напр. «pl, cs, uk, de?»), щоб можна було відповісти «так». Сам набір агент без відповіді не обирає: це рішення користувача, а не допущення. В evals такий сценарій зараховується як «поставив уточнення».
4. **Порівняння мов — лише за одним і тим самим QID.** Якщо точної статті в частині мов немає, агент:
   - повідомляє `no_article` як знахідку, а не як помилку: відсутність статті — теж сигнал;
   - аналізує точну статтю там, де вона є;
   - для порівняння всіх мов пропонує найближче ширше поняття, яке є в усіх мовах.

   Реальний випадок (перевірено 24.09): «intermittent fasting» (Q1666254) має cs і uk, але **не має pl**, і в pl.wikipedia немає статті під жодною назвою. Отже, перший приклад із завдання проходить саме цим шляхом: pl → `no_article`.
   - Спільне ширше поняття — «fasting» (Q44602), але це **слабка заміна**: pl «Post» насамперед про релігійний піст. Агент лише **пропонує** цей варіант, а в `assumptions` прямо пише: «broader concept, meaning differs (pl 'Post' is mostly religious fasting)».
   - Ближчий сигнал лише для pl — «Głodówka lecznicza» (лікувальне голодування). Агент може показати його окремо через `--article pl:Głodówka lecznicza` і прямо назвати, що це інша стаття.

**`analyze`** приймає:
- `--qid Q…` (можна кілька) або `--article <lang>:<Title>` для статей без Wikidata. Назва з `--article` перевіряється через MediaWiki, бо pageviews відповідає 404 і на «немає переглядів», і на «немає сторінки»: опечатка дає помилку, а не «нуль інтересу»; редирект веде на цільову статтю; сторінка неоднозначності дає помилку;
- `--langs pl,cs` (ISO-коди або англійські назви; `nb` → `no.wikipedia` тощо), обов'язковий з `--qid`. Мова з `--article` **додається автоматично** з рядком в `assumptions` («pl added to the compared languages for --article …»); з одними `--article` `--langs` можна не передавати. М'який ліміт 10 мов (разом із доданими); оцінка часу першого запуску пишеться в stderr;
- `--period 12m|24m|36m|5y` (за замовчуванням `24m`) або `--from YYYY-MM --to YYYY-MM`. Дати рахує скрипт, а не агент. Для `--from/--to`: період ≥ 12 місяців і разом із базою «рік до року» лежить у 72-місячному вікні, інакше помилка з найранішою допустимою датою (`the earliest --from is …` / `the earliest --to is …`); лише `--to` дає 24 місяці до нього, лише `--from` — до останнього повного місяця;
- `--rank-by growth|share|size` (за замовчуванням `growth`);
- `--report` — PNG + PDF; `--report-lang en|uk`; `--out <dir>` — ручне перевизначення папки. **За замовчуванням код сам обирає підпапку за параметрами запиту:** `./wds-output/<тема>_<мови>_<період>/` у поточній папці користувача, напр. `intermittent-fasting_pl-cs_24m` (для `--from/--to` — `2023-01-2026-08`). Назва лише ASCII (`Głodówka lecznicza` → `glodowka-lecznicza`), щоб шлях не зіпсувала консоль. Кожне питання у своїй папці: звіт іншої теми не перезаписується, а той самий запит оновлює свою;
- `--note "<рекомендація агента>"` — без чисел: відхиляється будь-яке слово, що складається лише з цифр і розділових знаків (`22%`, `2024`, `3.5`); слова з літерами на кшталт `B2C`, `COVID-19` дозволені. Помилка підказує, як переформулювати.

**Вивід у stdout:** компактний JSON (UTF-8, `ensure_ascii=False`), приблизно 20–40 рядків, числа округлені. Той самий JSON завжди пишеться в `result.json` поруч із файлами запуску, а без `--out` ще й у **`./wds-output/last-result.json`** — останній запуск, зокрема помилка. Це запасний варіант зі сталим ASCII-шляхом, якщо консоль зіпсувала кодування (разом із шляхами у виводі). Помилки теж пишуться, щоб агент ніколи не прочитав старий результат як новий. Назви статей у прикладі справжні, **числа — нулі-заповнювачі**; приклади для SKILL.md беремо лише зі справжнього виводу:
```json
{
  "status": "ok",
  "period": {"from": "2024-09", "to": "2026-08", "months": 24},
  "must_say": ["cs: interest is falling: views per million 0.0% year over year (…)", "…"],
  "assumptions": ["cs: topic measured by article 'Přerušovaný půst' (+N redirects)",
                  "views = human traffic (agent=user), all devices", "…"],
  "results": [
    {"qid": "Q1666254", "lang": "cs", "status": "ok", "title": "Přerušovaný půst",
     "views_last_12m": 0, "views_prev_12m": 0, "growth_pct": 0.0,
     "per_million_last_12m": 0.0, "per_million_growth_pct": 0.0,
     "trend": "rising", "confidence": "medium",
     "reasons": ["…"], "warnings": ["…"]},
    {"qid": "Q1666254", "lang": "pl", "status": "no_article"}
  ],
  "ranking": {"by": "growth", "order": [
    {"lang": "cs", "why": "highest relative growth, medium confidence"},
    {"lang": "sk", "why": "low confidence: listed after confident results"}]},
  "caveats": ["language edition ≠ country", "interest ≠ willingness to pay", "…"],
  "files": {"result_json": "…", "data_csv": "…", "chart_png": "…", "report_pdf": "…"}
}
```
- Мова без статті — завжди явний запис `"status": "no_article"`, ніколи не пропуск.
- **`must_say`** (додано 26.09 після T15, задача T13b) — 3–5 коротких англійських речень, які код складає з уже порахованих полів; агент передає **кожне** своєю мовою, не змінюючи змісту, а решту JSON бере для деталей. Причина: на Haiku повнота застережень коливалася між прогонами тієї самої SKILL.md (від 5/5 до 3/5), а в прикладі 3 модель переходила до порад про країни й ринки (`evals/results/p0-haiku-notes.md`, розд. 6). Стоїть одразу після `period`, щоб її не зрізало обрізання виводу. Пункти, за порядком:
  1. **Головний висновок** з `ranking` і `trend`: мови в порядку ранжування, слово тренду кожної й одне число з названою метрикою («views per million −46.4% year over year»); для `--rank-by size` — перегляди за 12 місяців. Low-довіра позначена в дужках.
  2. **Довіра:** рівень по мовах (однакові рівні згруповано) і головна причина, чому не вище — перше правило, що обмежило рівень (для high — «checks passed»).
  3. **`no_article`** — лише якщо є: «pl: no article on this topic: little local coverage; interest there cannot be measured this way».
  4. **Мовний розділ ≠ країна; інтерес ≠ готовність платити** — завжди, одним реченням: саме ці два застереження зупиняють перехід від переглядів до «ринків».
  5. **Ключове застереження за даними:** зміна фільтра ботів, якщо база «рік до року» перетинає 2025-03-20; інакше «одна стаття представляє тему».

  Числа в `must_say` дослівно ті самі, що в полях JSON (їх перевіряє `check_numbers.py`). Повні `reasons`, `warnings`, `caveats` лишаються в JSON і в PDF без змін; тексти — через `i18n`, як решта.
- **Ранжування** йде по мовах. Якщо QID кілька, тема = сума їхніх статей у мові: той самий вердикт (`trend`, `confidence`) рахується й по сумарному ряду мови (поле `topic_totals`), а деталі по кожній статті лишаються в `results`. Ранжування спирається на `topic_totals`. Результати з `confidence: low` ніколи не стоять вище за впевнені; кожна позиція має коротке `why`.

Помилки мають вигляд `{"status": "error", "error": "...", "hint": "..."}` і пишуться для агента: «unknown language 'polski', did you mean 'pl'?». Прогрес пишеться в stderr. Повні часові ряди йдуть у CSV, не в stdout.

## 4. Дані й метрики

**Завантаження**
- Pageviews API, `agent=user`, `all-access`, **щоденні** дані для статті та для всього розділу (`aggregate`). Місяці агрегуємо самі.
- **Фіксоване вікно завантаження**, вирівняне по місяцях: 72 повні місяці, що закінчуються останнім повним місяцем (5 років максимального періоду + 12 місяців бази для «рік до року»). Потрібний період вирізається локально. Тому URL запитів не змінюється весь місяць, і зміна `--period`, «додай sk» чи повторний запит беруть дані з кешу.
- «Останній повний місяць» — місяць, останній день якого вже є в API (дані запізнюються приблизно на добу, тож 1-го числа це ще позаминулий місяць).
- До 10 редиректів статті (MediaWiki `prop=redirects`, простір імен 0) додаються до ряду. Якщо редиректів більше, пишемо попередження. У CSV перегляди статті й редиректів ідуть окремими колонками.
- **CSV помісячний:** рядок на статтю × місяць за всі місяці, з яких пораховано хоч одне число в JSON (період + база «рік до року»), тож кожне число можна перерахувати. Колонки: `month, lang, qid, title, article_views, redirect_views, views, edition_views, views_per_million`; `article_views` — лише стаття (її й звіряємо з pageviews.wmcloud.org), `redirect_views` до T10 порожня. UTF-8 з BOM, щоб Excel показував ł, ř, ї.
- Назви кодуються в коді (`urllib.parse.quote`, UTF-8). 404 для знайденої статті означає нулі.
- Запити йдуть послідовно, приблизно 3/с. На 429/503 чекаємо `Retry-After` (якщо заголовка немає, то ≥5 с з експоненційною затримкою, максимум 5 спроб).
- `User-Agent: wikipedia-demand-signals/<версія> (+<URL репозиторію>)`, можна перевизначити через `WDS_USER_AGENT`. Email не вказуємо.
- Кеш: `%LOCALAPPDATA%/wikipedia-demand-signals` або `~/.cache/…`. Кожна відповідь записується одразу, тож повторний запуск після таймауту продовжує з місця зупинки. Pageviews за фіксоване вікно зберігаються назавжди, пошук і редиректи — 7 днів.

**Очищення рядів**
- Пропущені дні заповнюються нулями, але тільки після дати створення статті (перша правка). Ряд до створення обрізається, з попередженням. До T10 дата появи = перший місяць із переглядами (він неповний, тож повні місяці рахуються з наступного).
- Якщо попередні 12 місяців покриті не повністю (статтю створено пізніше), то `growth_pct: null` і `per_million_growth_pct: null` з попередженням. Зростання «з нуля» не рахуємо.
- Неповний поточний місяць відкидається.
- Різка стійка зміна рівня (≥3× між медіанами сусідніх вікон) дає попередження: «можливе перейменування або зміна в усьому розділі».

**Метрики (на кожну статтю × мову)**
- `views_last_12m`, `views_prev_12m`, `growth_pct` — розмір аудиторії та зростання «рік до року» (прибирає сезонність).
- `per_million_*` — частка від усіх переглядів розділу. Прибирає ефект розміру розділу та загальні зміни трафіку Wikipedia.
- Тренд: Theil-Sen (нахил) + Mann-Kendall (стійкість) по **місячному** нормалізованому ряду; реалізація на numpy.
- **Сплеск (T12)** — пік, якого немає в тому самому місяці сусіднього року. Місяць — кандидат, якщо його перегляди в `SPIKE_RATIO` разів вищі за медіану сусідніх місяців; це сплеск, лише якщо той самий місяць сусіднього року такого піку не має (його відношення до своїх сусідів нижче порога). Сезонний пік повторюється щороку і сплеском не є: у uk «Астрономія» вересень 2024 (4 687 проти ~1 700 поруч) схожий на шкільну сезонність: 1–24 вересня 2025 і 2026 — 1 454 і 889 переглядів проти 285 і 275 за 1–24 серпня (перевірено 25.09). Перевіряємо **в обох вікнах порівняння** (останні 12 місяців і попередні 12): сплеск у базі так само спотворює ріст, як і в останньому році. Поріг і ширина «сусідства» — іменовані константи, підбираються в T12 на синтетичних рядах і на реальних випадках (uk «Астрономія» 2024-09 — сезонність; pl «Astronomia» 2025-11 — сплеск).
- Обсяг: медіана переглядів за місяць **за 24 місяці, з яких рахується ріст** (незалежно від `--period`: з `5y` стаття, велика кілька років тому, але мала зараз, інакше проходила б перевірку; реальний випадок — cs «Přerušovaný půst»). Місяці до появи статті не враховуються. Якщо медіана дуже мала, ряд вважається шумним.

**Вердикт.** Правила явні, з порогами, без зваженого балу.
- **`trend` визначає один сигнал:** нормалізований ріст «рік до року» (`per_million_growth_pct`): ≥ +10 % → `rising`, ≤ −10 % → `falling`, інакше `flat`; `null` → `insufficient_data`. Mann-Kendall і Theil-Sen впливають **лише** на `confidence`.
- Якщо сирий і нормалізований ріст мають різні знаки (розділ загалом падає, а частка теми росте), то `reasons` пояснює це прямо: «absolute views fell X %, while the whole edition fell Y %».
- **`confidence`.** Базові умови: обсяг достатній, немає сплесків і попереджень, ≥ 24 місяців даних. Далі залежить від `trend`:
  - **rising / falling:**
    - **high** — Mann-Kendall значущий у тому ж напрямку, сирий і нормалізований ріст одного знака, базові умови виконані;
    - **medium** — не виконана рівно одна умова (зокрема, різні знаки сирого й нормалізованого росту або незначущий Mann-Kendall);
    - **low** — Mann-Kendall значущий у **протилежному** напрямку («signals disagree») або не виконано ≥ 2 умови.
  - **flat:**
    - **high** — Mann-Kendall незначущий і базові умови виконані;
    - **medium** — Mann-Kendall значущий («slow steady drift, under 10 % a year») або не виконана одна базова умова;
    - **low** — не виконано ≥ 2 умови.
  - **insufficient_data** — завжди low.
  - Незалежно від трендів: малий обсяг, зміна рівня або < 12 місяців даних → не вище **low**.
  - **Тимчасове правило P0 (знімається в T12):** поки немає Mann-Kendall і перевірки сплесків, результат не може показати, що він стійкий, тож `confidence` не вище **medium**; у `reasons` — рядок «capped at medium until trend stability and one-off spikes are checked». Реальний випадок: uk «Астрономія» з піком у базі проходила всі перевірки P0 як high.
Пороги — іменовані константи з обґрунтуванням у коді й `references/methodology.md`, підібрані на синтетичних рядах. p-value користувачу не показуємо. Кожне правило, що спрацювало, додає рядок у `reasons`.

**Незмінні застереження (`caveats`)**, однакові в JSON і PDF: мовний розділ ≠ країна; інтерес ≠ готовність платити; одна стаття представляє тему; фільтр ботів (`agent=user`) неідеальний; **з 2025-03-20 Wikimedia фільтрує ботів суворіше, раніші дані не перераховано**, тож ріст через цю дату частково відображає зміну правил. Джерела: [Wikitech, Data Issues 2025-06-03](https://wikitech.wikimedia.org/wiki/Data_Platform/Data_Lake/Data_Issues/2025-06-03_May_2025_spike_in_bot_traffic) (новий евристичний фільтр від 2025-08-28, дані перераховано від 2025-03-20), [Diff, 2025-10-17](https://diff.wikimedia.org/2025/10/17/new-user-trends-on-wikipedia/) (людські перегляди −8 % рік до року після перерахунку).

**Звіт (`--report`)**
- PNG: помісячні перегляди на мільйон та абсолютні перегляди по мовах.
- PDF A4, 1 сторінка: заголовок і параметри, таблиця метрик, графік, вердикти з причинами, `note` агента, незмінні застереження, джерела й дата.
- Усі цифри та тексти в PDF беруться з шаблону (en/uk), а агент дає лише `note`.

## 5. Структура проєкту

Корінь репозиторію = директорія навички (назва папки = `name` у SKILL.md).
```
wikipedia-demand-signals/
  SKILL.md                 ← для агента (EN): коли використовувати, робочий процес, 2 команди, як читати JSON, що обов'язково сказати
  README.md                ← для людей (UK): логіка, рішення, обмеження, як перевіряли, план розвитку
  requirements.txt / requirements-dev.txt
  scripts/
    wds.py                 ← CLI (PEP 723 заголовок), тільки парсинг аргументів і вивід
    wds_lib/               ← api.py (HTTP, кеш, ліміти), resolve.py, langs.py, pageviews.py,
                              series.py (очищення), stats.py (MK, Theil-Sen), verdict.py,
                              analyze.py (збирає команду analyze і файли), report.py, i18n.py
  references/methodology.md ← метрики й пороги (UK), агент читає лише на питання «чому»
  evals/evals.json + evals/results/  ← запити, критерії, підсумки прогонів на Haiku
  evals/check_numbers.py   ← автоперевірка «кожне число у відповіді є в result.json» (з допуском на округлення)
  tests/                   ← pytest + fixtures (записані відповіді API)
  docs/SPEC.md, docs/plan.md, docs/todo.md
```
Мова: усе, що читає агент (SKILL.md, JSON, помилки), англійською; документи для людей українською.

**SKILL.md:**
- Фронтматер: `name`; `description` (третя особа, що робить + коли використовувати); `compatibility: Requires internet access to Wikimedia APIs and Python 3.11+ (uv recommended)`.
- `allowed-tools`, звужений до самого скрипта, два шаблони: `Bash(uv run "${CLAUDE_SKILL_DIR}/scripts/wds.py" *)` і запасний `Bash(python -m uv run "${CLAUDE_SKILL_DIR}/scripts/wds.py" *)` (uv, встановлений через pip, часто не потрапляє в PATH — так на машині розробки; без другого шаблону запасна команда впирається в запит дозволу, а в `claude -p` — у відмову). Кожен шаблон має **буквально** збігатися з командою в SKILL.md, включно з лапками. Перевіряємо в тестовій папці з пробілом у шляху.
- `allowed-tools` лише дозволяє команду заздалегідь, і тільки в тому ході, де викликано навичку. Агента в Bash воно не спрямовує. Тому:
  - у тексті прямо пишемо «run via the Bash tool»;
  - у тестову папку для ручного прогону в застосунку кладемо `.claude/settings.json` з правилами-дозволами; вони діють лише тоді, коли папці довірилися.
- **Автоматичні прогони (`claude -p`, evals) передають ті самі 4 правила прапорцем `--allowedTools`**: `Skill(wikipedia-demand-signals)`, `Skill(wikipedia-demand-signals *)` і обидва шаблони Bash з абсолютним шляхом навички в тестовій папці. Причина (T9, нотатки розд. 0): у недовіреній папці правила `settings.json` відкидаються, `allowed-tools` навички не діють, а виклик навички з `allowed-tools` сам потребує дозволу `Skill(...)`, і в `-p` будь-який запит дозволу = відмова. Сесійні правила не залежать від довіри, тож прогін відтворюється в кожній новій чистій папці й на будь-якій машині. Це налаштування тестового оточення: правила ті самі, що в `settings.json`, і нічого понад команди навички не дозволяють.
- **Перевірка в довіреній папці (T15, Claude Code 2.1.281, нотатки розд. 6):** `allowed-tools` навички діють лише тоді, коли навичку викликає **користувач** командою `/wikipedia-demand-signals …`: обидві команди (`uv run`, потім `python -m uv run`) пройшли без жодного питання. Коли навичку обирає **модель** (інструмент `Skill`), поле не діє ні в `claude -p`, ні в режимі застосунку (stream-json), навіть для пробного `Bash(python -c *)`; правила `settings.json` довіреної папки при цьому діють. **Поле лишаємо:** через `/…` воно прибирає всі питання про дозвіл, а коли навичку обирає модель, коштує одне питання «Execute skill» (без поля там однаково було б питання на кожну команду). README пояснює обидва шляхи й правило для `settings.json`.
- Команди пишемо з `${CLAUDE_SKILL_DIR}` і пояснюємо для інших агентів, що це папка, де лежить SKILL.md.
- Окремий рядок: «якщо назви в консолі спотворені, прочитай `wds-output/last-result.json`».
- **Обсяг:** ≲ 170 рядків (після T15), і з P1 SKILL.md не росте: нове правило або замінює старе, або переходить у код. Так, `must_say` (розд. 3) замінює в «What to tell the user» обов'язкове закінчення «Assumptions + Caveats» і переказ кожного рядка `reasons`; у SKILL.md лишається те, чого код знати не може: яку статтю обрав агент і чи вона лише проксі теми.

## 6. Стиль коду

Невеликі чисті функції, type hints, без класів там, де вистачає функцій. Константи мають імена й пояснення, «магічних чисел» немає.
```python
# A topic with fewer than ~300 views/month moves by tens of percent from noise alone;
# growth on such a base is reported but never above "low" confidence.
MIN_MEDIAN_MONTHLY_VIEWS = 300

def growth_pct(last: float, prev: float) -> float | None:
    """Year-over-year change in percent; None when the base is zero."""
    return None if prev == 0 else round((last - prev) / prev * 100, 1)
```
`ruff` із налаштуваннями за замовчуванням.

## 7. Тестування

1. **Юніт-тести на синтетичних рядах із відомою відповіддю:** рівний ряд + один сплеск → не «rising», low; лінійне зростання з шумом → rising; чиста сезонність → flat; стрибок рівня → попередження; коротка історія → low; малий обсяг → low.
2. **Статистика:** Mann-Kendall / Theil-Sen звіряються з `scipy` на випадкових рядах.
3. **Очищення даних:** заповнення нулями, відкидання неповного місяця, обрізання за датою створення, `growth_pct: null` для молодої статті, мапінг мов, валідація `--note` (`22%` відхиляється, `B2C` і `COVID-19` проходять), сортування кандидатів у `resolve`, ранжування (low ніколи не першим).
   Окремий тест: версії залежностей у заголовку PEP 723 і в `requirements.txt` збігаються.
4. **Інтеграційні тести без мережі:** записані відповіді API в `tests/fixtures/`. Один живий smoke-тест позначений окремо.
   **У P0** записуються справжні відповіді `resolve` для 5 запитів: astronomy, intermittent fasting, learning English, Java, Mercury. На них тести перевіряють сортування, фільтр сторінок неоднозначності й кандидатів із 0 статей, а також `ambiguous` (очікування: розд. 3; для «learning English» — VOA першим за збігом, але без `ambiguous`; для «intermittent fasting» — Q1666254 першим, не «fasting», і `sitelinks.pl = null`).
5. **Ручна звірка** 2–3 статей із pageviews.wmcloud.org. Звіряємо колонку «лише стаття», бо сайт не додає редиректи. Результат записується в README.
6. **Evals на Haiku** (через `skill-creator`, коли пишемо SKILL.md): ≥ 5 запитів — 3 з завдання, уточнення «додай мову / зміни критерій», неоднозначна тема або мова без статті. Для кожного запиту два прогони, із навичкою і без неї (база для порівняння), на субагентах Haiku. Критерії: викликав resolve → analyze; кожне число у відповіді є в JSON; назвав рівень довіри й застереження; перепитав за неоднозначності або коли мовні розділи не названі; PDF є, коли просили. Плюс один ручний прогін `claude --model haiku` у чистій папці, куди навичка підключена через junction у `.claude/skills/`.
   **Умови прогону на Haiku:** кожен прогін — у новій чистій папці з пробілом у шляху (лише junction навички, без `wds-output/` попередніх прогонів: у T9 старі результати в папці підмінили відповідь); дозволи — прапорцем `--allowedTools` (розд. 5); бюджет списку навичок — за замовчуванням, бо обрізаний `description` — реальна умова, яку навичка має витримати.
